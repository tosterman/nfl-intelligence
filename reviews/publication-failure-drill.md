# Publication failure drill and receipt preservation

The receipt ledger previously used direct destination writes in both the native Git publisher and the direct Vercel receipt command. They now share a writer that serializes to a unique adjacent temporary file, rejects nonfinite JSON values, flushes and fsyncs the file, closes it, then replaces the destination atomically. Exceptions clean up the temporary file. Existing receipt bytes are not modified until replacement succeeds.

Eight Git-publication tests cover trusted deployment attribution and exact artifact comparison, alias propagation retry, status lookup failure, persistent mismatch timeout, orchestration failure recovery, atomic replacement failure and failed serialization. The disk-failure test injects both fsync and replace failures, verifies byte-for-byte preservation and no remaining temporary file, then confirms a successful replacement. The orchestration test isolates the filesystem and stubs Git/capture calls; failed deployment and mismatch timeout leave existing receipts unchanged while retaining the source-commit recovery manifest. These tests do not disrupt production or claim an actual provider outage was exercised.

Independent review found no blocker and separately reproduced an fsync failure. Both publication callers use the shared writer. Windows replacement occurs after the temporary file is closed. Scope: this provides atomic replacement and the tested failure behavior; it does not introduce concurrent-writer locking or guarantee directory-entry durability through power loss. Workflow concurrency and Git conflict handling remain separate controls.

Local verification passed all 124 Python tests. The eight publication-specific tests were rerun after adding the fsync case and passed. GitHub health workflow history filtered by `event=schedule` returned no runs at this inspection; successful manually dispatched probes must not be represented as sustained clock-triggered operation.
